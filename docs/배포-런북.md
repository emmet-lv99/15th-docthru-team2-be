## 1. 전체 흐름

```text
[팀원] feature 브랜치 → push → PR(base: develop)
        └→ GitHub Actions CI (자동 검사 · postgres 자동 준비)
        └→ 이상 없음 → merge → develop 반영
                                        │
[우리] develop → PR(base: main) → 리뷰 → merge
        └→ Cloud Build (자동) → 빌드 → 이미지 push → Cloud Run 배포 🚀
        └→ 3~5분 후 반영
```

| 단계 | 도구 | 소요 |
|---|---|---|
| CI 자동 검사 | GitHub Actions `ci.yml` | 3~5분 (postgres 준비 포함) |
| 자동 배포 | Cloud Build (`cloudbuild.yaml`) | 5~6분 |

| 주소 | 값 |
|---|---|
| 백엔드 (prod) | `https://docthru-be-xwfe2o3yfa-du.a.run.app` |
| 헬스 체크 | `https://docthru-be-xwfe2o3yfa-du.a.run.app/api/v1/ping` → `{"message":"pong"}` |
| Swagger | `https://docthru-be-xwfe2o3yfa-du.a.run.app/api-docs/` |

## 2. 브랜치 규칙

| 브랜치 | 하는 일 | PR base | 보호 규칙 |
|---|---|---|---|
| feature (개인) | 자기 도메인 구현 | → `develop` | 없음 |
| **develop** | 검증된 통합본 | ← feature | PR 필수 + CI 필수 |
| **main** | 발표용 확정본 | ← develop | PR 필수 + CI 필수 + 리뷰 1개 |

**처음 작업하기 전에 (한 번만)**

```bash
git checkout develop
git pull origin main     # main 의 뼈대·인프라를 develop 으로 당겨옵니다
```

> `develop` 은 `main` 보다 뒤처져 있을 수 있어요. 위 한 줄로 당기고 시작하면 됩니다.

**자기 브랜치 만들기**

```bash
git checkout -b feat/<내도메인>
```

## 3. CI 는 언제 돌까

`.github/workflows/ci.yml` 의 트리거:

| 이벤트 | 대상 | 검사 |
|---|---|---|
| `pull_request` | develop PR · main PR **둘 다** | ✅ |
| `push` | `main` · `develop` | ✅ |
| `workflow_call` | deploy.yml 이 재사용 | ✅ |

**CI 가 하는 일 (순서대로)**

| 스텝 | 내용 |
|---|---|
| Install | `pnpm install --frozen-lockfile` |
| Prisma contract emit | 계약 원본 → `contract.json` 재생성 (드리프트 점검) |
| **Database init** | **CI 전용 postgres** 에 계약대로 테이블 생성 |
| Lint | `pnpm lint` |
| Format check | `pnpm format:check` |
| Test | `pnpm test` |
| Build image | `docker build` — 이미지가 올라가는지까지 확인 |

> **비밀값이 하나도 필요 없습니다.** CI 는 GitHub Actions runner 안에서 `postgres` 서비스 컨테이너를 직접 띄우고
> `postgresql://docthru:docthru@localhost:5432/docthru_test` 에 연결해요. 운영 DB 에는 손대지 않습니다.

> ℹ️ 계약 테스트(`pnpm test:contract`)는 CI 에서 돌리지 않습니다.
> 도메인 구현 전에는 "8초록/41빨강" 이 정상이라 CI 를 항상 빨갛게 만들기 때문이에요.
> 구현하며 초록을 늘려갈 때 로컬에서 `pnpm test:contract` 로 확인하면 됩니다.

## 4. 자동 배포 (Cloud Build)

| 항목 | 값 |
|---|---|
| 트리거 | `Build-and-deploy-to-Cloud-Run-service-docthru-be-on-push-to-main` |
| 감시 브랜치 | `^main$` (develop 은 **배포하지 않습니다**) |
| 설정 파일 | [`cloudbuild.yaml`](./cloudbuild.yaml) (repo 안에서 버전 관리) |
| 이미지 | `asia-northeast3-docker.pkg.dev/th-docthru-team2-be/cloud-run-source-deploy/15th-docthru-team2-be/docthru-be:<커밋해시>` |
| Cloud Run 서비스 | `docthru-be` (리전 `asia-northeast3`) |
| 인스턴스 상한 | 3 (무료 티어 과금 방지) |

> ⚠️ **배포 스텝은 `--set-env-vars` 를 주지 않습니다.** 환경변수는 Cloud Run **서비스에 등록**되어 있고,
> 이미지 교체 때 그대로 유지돼야 해요. (`--set-env-vars` 를 주면 목록 전체가 교체돼서 다른 변수가 사라집니다)
>
> ⚠️ **GitHub Actions 의 `deploy.yml` 은 예비(수동) 경로**입니다. 공식 자동 배포는 Cloud Build 가 담당해요.
> 다만 `deploy.yml` 에는 **DB 마이그레이션** 스텝이 있어서, 스키마를 같이 올리고 싶을 때 씁니다.

## 5. 환경변수 8종 (Cloud Run)

```bash
gcloud run services describe docthru-be \
  --project=th-docthru-team2-be --region=asia-northeast3 \
  --format="value(spec.template.spec.containers[0].env)"
```

| 이름 | 값 | 비고 |
|---|---|---|
| `NODE_ENV` | `production` | `development` 면 dev-login 우회로가 열림 |
| `DATABASE_URL` | `postgresql://postgres.<ref>:<비밀번호>@aws-0-ap-northeast-2.pooler.supabase.com:5432/postgres` | ⚠️ **Session pooler** (direct 는 IPv6 전용이라 Cloud Run 불가) |
| `JWT_ACCESS_SECRET` | 64자 base64 | 32자 이상 |
| `JWT_REFRESH_SECRET` | 64자 base64 (**위와 다른 값**) | 스키마 `refine` 로 강제 |
| `CLIENT_BASE_URL` | `https://docthru-alysvay2yq-du.a.run.app` | 프론트 주소 (CORS 허용 대상) |
| `CORS_ORIGINS` | `https://docthru-alysvay2yq-du.a.run.app` | 프론트 주소 |
| `API_BASE_URL` | `https://docthru-be-xwfe2o3yfa-du.a.run.app/api/v1` | OAuth 콜백 주소 계산용 |
| `DB_POOL_MAX` | `5` | `max-instances(3)` 와 곱해 15 세션 (Supabase Free 한도 내) |

**값을 바꿀 때 (주의)**

```bash
# ⚠️ --set-env-vars 는 env 목록 전체를 교체합니다.
#    일부만 넣으면 JWT 값 등이 사라져서 컨테이너가 listen 전에 죽어요.
#    그래서 8종을 항상 통째로 다시 넣으세요.
gcloud run services update docthru-be \
  --project=th-docthru-team2-be --region=asia-northeast3 \
  --set-env-vars="NODE_ENV=production,DATABASE_URL=...,JWT_ACCESS_SECRET=...,JWT_REFRESH_SECRET=...,CLIENT_BASE_URL=...,CORS_ORIGINS=...,API_BASE_URL=...,DB_POOL_MAX=5"
```

> 일부만 바꾸고 싶다면 `--update-env-vars` 를 쓰세요.

## 6. 스키마 규칙 — contract 를 바꾸면

**테이블은 이미지가 아니라 DB 쪽에 있습니다.** 그래서 contract 를 바꿨다면(main 머지 후) DB 를 한 번 맞춰야 합니다.

```bash
# ① DB 주소 주입한 상태에서
export DATABASE_URL='postgresql://postgres.<ref>:<비밀번호>@aws-0-ap-northeast-2.pooler.supabase.com:5432/postgres'

# ② 계약대로 테이블 만들기 + 서명
pnpm exec prisma db init

# ③ 검증
pnpm exec prisma db verify     # → "Database marker and schema match contract"
```

| Prisma 8 명령 | 하는 일 |
|---|---|
| `db init` | DB 를 계약에 맞춰 만들고 **서명** |
| `db schema` | 실스키마 확인 |
| `db sign` | 계약 서명 |
| `db update` | 스키마를 계약에 맞춤 |
| `db verify` | 계약 ↔ 실스키마 일치 검증 |
| `db migrate` | 마이그레이션 적용 (리팩터링 성격 변경 시) |

> ⚠️ `db init` 은 **추가만** 합니다(additive). 기존 데이터를 지우지 않아요.
> 데이터를 지우는 마이그레이션은 `db migrate` 를 쓰고, **반드시 멈추고 리뷰**하세요.

> 📌 자동화하려면 Secret Manager + 배포 스텝이 필요합니다. 지금은 위 1회 실행이 더 단순해서 수동으로 합니다.

## 7. 시드는 로컬 전용

`scripts/seed-safety.js` 가 아래 3가지를 강제합니다.

| # | 검사 | 이유 |
|---|---|---|
| ④ | 호스트가 `localhost` / `127.0.0.1` / `db` | 실수로 원격 DB 를 지우지 못하게 |
| ⑤ | DB 이름이 `docthru_bp` | 시드가 **전부 지우고 다시 넣는** 스크립트라 대상 확인 |
| ⑥ | `--allow-reset=docthru_bp` 인자 | 이중 확인 |

→ **원격 DB(Supabase) 에서는 시드가 실행되지 않습니다.** 운영 데이터는 팀원이 직접 가입하면서 쌓으면 됩니다.
→ 로컬에서만: `docker compose up` 후 `pnpm seed`

## 8. 로컬 개발 3단계

```bash
# ① 로컬 DB 띄우기 (postgres)
docker compose up -d

# ② 환경변수 준비
mkdir -p env && cp .env.example env/.env.development

# ③ 개발 서버
pnpm dev        # http://localhost:5010
```

| 자주 쓰는 명령 | 하는 일 |
|---|---|
| `pnpm dev` | 개발 서버 (`.env` 로 DB 주소 읽음) |
| `pnpm test` | 테스트 |
| `pnpm test:contract` | 계약 테스트 (구현 진행 확인용) |
| `pnpm db:init` | 로컬 DB 를 계약대로 생성 |
| `pnpm seed` | 로컬 DB 에 데모 데이터 (위 안전장치 참고) |
| `pnpm lint` / `pnpm format` | 린트 / 포맷 |

> ⚠️ `env/.env.development` 은 **gitignore 대상**입니다. 실제 비밀값은 절대 커밋하지 마세요.
> 파일 이름이 정확해야 해요 — `development` 철자 그대로 (`dvelopment` 로 typo 내면 조용히 안 읽힙니다).

## 10. 자주 나는 문제

| 증상 | 원인 | 해결 |
|---|---|---|
| `failed to start and listen on PORT=8080` | 필수 env 3종 누락 → import 단계에서 종료 | 리비전 로그에서 `환경 변수 검증 실패` 검색 → 8종 통째로 다시 주입 |
| `환경 변수 검증 실패` | `DATABASE_URL` 형식 오류 / JWT 32자 미만 / 두 JWT 가 같음 | §5 표 조건 확인 |
| 주소는 열리는데 Cloud Run 안내 페이지 | 이미지가 `gcr.io/cloudrun/placeholder` | 이미지 push 후 `services update` 로 실제 이미지 지정 |
| `Corepack … HTTP 503` | corepack 이 npm 레지스트리 메타데이터를 못 받음 | Dockerfile 이 tarball 직접 설치 방식 (적용 완료) |
| `the --mount option requires BuildKit` | Dockerfile 에 BuildKit 전용 문법 | `RUN --mount=type=cache` 사용 금지 |
| `too many connections` | 세션 과다 | `max-instances=3` · `DB_POOL_MAX=5` 로 맞추기 |
| `password authentication failed` | Supabase 비밀번호 오타 / URL 인코딩 | 영문·숫자만으로 비밀번호 리셋 후 다시 받기 |
| DB 는 되는데 API 가 500 | 테이블이 없음 | `pnpm exec prisma db init` (단, env 주입 후) |

## 11. 브랜치 보호 규칙 설정 (repo 소유자가 해야 합니다)

> ⚠️ **현재는 보호 규칙이 없어서 아무나 `main` 에 바로 push 할 수 있습니다.**
> 아래를 repo 소유자(`emmet-lv99`) 계정으로 한 번만 설정해 주세요.

**콘솔로**

1. `Settings` → `Branches` → `Add rule`
2. **Branch name pattern** → `main`
3. ✅ `Require a pull request before merging`
4. ✅ `Require status checks to pass before merging` → **`verify` 추가**
5. ✅ `Do not allow bypassing the above settings`
6. 같은 방법으로 `develop` 도 추가 (리뷰 개수는 0 으로 두면 됩니다)

**터미널로 (admin 권한이 있는 계정에서)**

```bash
gh api -X PUT repos/emmet-lv99/15th-docthru-team2-be/branches/main/protection \
  --input '{"required_status_checks":{"strict":true,"contexts":["verify"]},"enforce_admins":true,"required_pull_request_reviews":{"required_approving_review_count":1,"dismiss_stale_reviews":true},"required_conversation_resolution":true,"allow_force_pushes":false,"allow_deletions":false}'
```

> 상태 체크 이름은 워크플로 job 이름인 **`verify`** 입니다.
